# Deploy (free-tier friendly)

StockIQ is a FastAPI backend plus a static React frontend. The backend fails closed in
production: missing or unsafe settings stop startup rather than falling back to demo values.

## 1. Required production environment variables

| Variable | Requirement |
|---|---|
| `ENVIRONMENT` | `production` (set by `render.yaml`) |
| `DATABASE_URL` | Explicit MySQL/MariaDB **or PostgreSQL** URL with credentials **and verified TLS** (see below) |
| `JWT_SECRET` | Strong random value, at least 32 characters; generated by Render when using the blueprint |
| `CORS_ORIGINS` | Exact frontend origin(s), comma-separated. No `*`. |
| `ADMIN_PASSWORD` | Explicit strong bootstrap password; `admin12345` is rejected |
| `STAFF_PASSWORD` | Explicit strong bootstrap password; `staff12345` is rejected |
| `JWT_EXPIRE_MINUTES` | Optional (default `480`) |
| `DOCS_ENABLED` | Optional, defaults to `false` in production; blueprint sets `false` |
| `OPENAPI_ENABLED` | Optional, defaults to `false` in production; blueprint sets `false` |

Generate a JWT secret with `openssl rand -hex 32` if you are not using the Render blueprint.
Never paste real secret values into `render.yaml`, Dockerfiles, or this repository.

`docker-compose.yml` is **local development only**. Copy `docker-compose.env.example` to `.env`
and fill it before running `docker compose up`. It sets `ENVIRONMENT=development` and has no
hardcoded fallback database, root or demo passwords.

## 2. Database and TLS

Create a hosted MySQL 8 (Aiven, Railway, TiDB Serverless, PlanetScale) **or PostgreSQL 14+**
database. Use a dedicated application user, not `root`/`postgres`, and grant only the application
schema.

Production **requires certificate-verified TLS** for either backend. A URL without TLS options is
rejected at startup. MySQL rejects `ssl_mode=DISABLED|PREFERRED|REQUIRED` and `ssl_disabled=true`;
PostgreSQL rejects `sslmode=disable|allow|prefer|require`.

Accepted MySQL forms:

```text
mysql+pymysql://app_user:PASSWORD@host:3306/stockiq?ssl_mode=VERIFY_IDENTITY&ssl_capath=/etc/ssl/certs
mysql+pymysql://app_user:PASSWORD@host:3306/stockiq?ssl_mode=VERIFY_IDENTITY&ssl_ca=/etc/ssl/certs/provider-ca.pem
mysql+pymysql://app_user:PASSWORD@host:3306/stockiq?ssl_capath=/etc/ssl/certs&ssl_mode=VERIFY_CA
```

PyMySQL only enforces hostname checks when a CA file or CA directory is present, so `ssl_ca`
or `ssl_capath` is mandatory in production. If the provider uses a private CA, mount that CA
into the container at the path used in the URL. A wrong path fails closed; do not weaken TLS to
work around it. TLS query options are translated into PyMySQL connection arguments and removed from
the SQLAlchemy engine URL, so they are not logged with connection details.

Accepted PostgreSQL forms (libpq):

```text
postgresql+psycopg://app_user:PASSWORD@host:5432/stockiq?sslmode=verify-full&sslrootcert=/etc/ssl/certs/provider-ca.pem
postgresql+psycopg://app_user:PASSWORD@host:5432/stockiq?sslmode=verify-ca&sslrootcert=/etc/ssl/certs/provider-ca.pem
```

`sslrootcert` is mandatory in production. `sslmode=verify-full` additionally verifies the hostname.
These options are translated into psycopg `ssl`/`sslmode` connection arguments and stripped from the
logged URL. MySQL TLS handling stays in `app/tls.py`; PostgreSQL TLS handling is in
`app/postgres_tls.py`. Never point production at a managed test instance such as Supabase.

## 3. Backend deployment

Render: create the web service from `render.yaml`. It sets `ENVIRONMENT=production`, uses
`/health/ready` as the health check, and leaves all secret values unset/synced from the platform.

The container command runs `python -m scripts.bootstrap` before uvicorn. Bootstrap is idempotent
and only creates the demo business, default warehouse, roles and the two users when they do not
exist. In production it refuses to create users without `ADMIN_PASSWORD` and `STAFF_PASSWORD`, and
rejects the old demo defaults.

Endpoints:

- `GET /health` — liveness only (process is up).
- `GET /health/ready` — readiness; executes `SELECT 1` and returns `503` if the database is unreachable.

`/docs`, `/redoc` and `/openapi.json` are disabled by default in production. Keep them disabled
unless you intentionally expose API documentation.

Log output is structured JSON on stdout. Secrets and bearer tokens are redacted; unhandled errors
return a generic `500` and log only exception type metadata.

## 4. Database startup and migrations

`Base.metadata.create_all(engine)` runs at startup and in bootstrap. It is safe for the **first
deployment against an empty schema**: it only issues `CREATE TABLE IF NOT EXISTS`-style checks and
never drops or rewrites existing tables.

It is **not** a migration system. It will not add columns, change types, create indexes on existing
tables, or backfill data.

Safe strategy:

1. First deploy: let bootstrap create the initial schema, then verify tables and login.
2. Later changes: add a reviewed, versioned SQL file under `db/migrations/` and apply it as a
   separate release step before rolling the new app version. Prefer backward-compatible additive
   changes: add nullable columns, backfill, then add constraints in a later release.
3. Take a `mysqldump --single-transaction` backup (MySQL) or a `pg_dump -Fc` backup (PostgreSQL)
   before any schema change, rehearse on a staging copy, and avoid destructive changes in the same
   release as application code. See [`docs/backup.md`](backup.md).
4. Introduce Alembic only when schema changes become frequent enough to justify it.

## 5. Frontend deployment

Build `frontend/` with `VITE_API_URL=https://<api-host>`. This value is baked into the bundle and
must match `CORS_ORIGINS` on the backend. It is a public URL, not a secret.

The JWT is kept in tab-scoped `sessionStorage`, attached as `Authorization: Bearer <token>`, and
cleared on logout or any `401`. This limits persistence compared with `localStorage` but remains
XSS-sensitive. A Content Security Policy is the practical mitigation in this phase; HttpOnly
cookies plus CSRF protection remain a future hardening option.

Security headers are applied in three places:

- Vite dev server: relaxed CSP for React Refresh and `ws://localhost:*` HMR.
- Vite preview and generated `dist/_headers`: strict production CSP, `nosniff`, `X-Frame-Options`,
  `Referrer-Policy`, `Permissions-Policy` and HSTS.
- FastAPI responses: API-specific CSP (`default-src 'none'`), `nosniff`, `no-referrer`,
  `X-Frame-Options`, `Permissions-Policy` and HSTS in production.

`dist/_headers` is generated at build time from `VITE_API_URL` and is honored by hosts such as
Netlify and Cloudflare Pages. Vercel does not use `_headers` for all deployment modes; add the
equivalent entries to `vercel.json` there. Verify with `curl -I https://<frontend-host>` after
deployment.

The charting library is split into an async `charts` chunk. Login, the application shell and
navigation remain in the initial bundle; heavy routes load through React.lazy/Suspense.

## 6. Deployment checklist

- [ ] Hosted MySQL or PostgreSQL created with a dedicated non-root user and verified TLS configured.
- [ ] All required backend env vars set in the platform dashboard; no secrets in the repo.
- [ ] `CORS_ORIGINS` exactly matches the frontend origin.
- [ ] `/health/ready` returns `200` after deploy and `503` when the DB is stopped in staging.
- [ ] `/docs` and `/openapi.json` return `404` in production.
- [ ] Login works and demo bootstrap credentials no longer work.
- [ ] Frontend response includes the expected CSP and HSTS headers.
- [ ] Backup and migration procedure reviewed before any schema change.
